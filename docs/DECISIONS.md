Décisions techniques

Statut : D1 à D8 (socle) proposées, à valider en équipe (tâche 0.1) et avec le tuteur. D9 et suivantes ont été prises pendant la construction de la démo (octobre 2026) ; chacune indique ce qui la remettrait en cause. Pour en changer une : PR qui modifie ce fichier.

Socle
D1 — Stack. Next.js (App Router) + TypeScript + Prisma + PostgreSQL 16, suggérée par le dossier tutrice. Un seul langage, un seul dépôt.
D2 — Monolithe modulaire. Un seul projet, un dossier par phase dans src/modules/ (carte : src/modules/registry.ts).
D3 — Schéma. Part de l'Annexe B du dossier. Écarts : Consumption a une contrainte d'unicité (EFA, année, énergie) ; ConsumptionMonth ajoute source, confidence, validated ; DjYear et ClimateZone sont séparées ; champs « type » en texte validé côté code (src/lib/domain.ts), pas en enum SQL, pour pouvoir en ajouter sans migration.
D4 — Écriture commune des consommations. saveConsumption : une valeur déjà validée par l'utilisateur n'est jamais écrasée par une valeur non validée ; chaque mois garde sa source.
D5 — Données réelles et données fictives (remplace la version initiale « tout est fictif »). Sont réels et sourcés : les DJU mensuels (stations Aulnois-sous-Laon 02037002 et Saint-Quentin 02320001, fournis par Mira), les valeurs Cabs de l'arrêté du 1er août 2025 (data/referentiels/operat/cabs_CAP18_restauration.json) et, avec la tâche « référentiel OPERAT », le référentiel d'activités v9.0 et la table département → zone. Restent fictifs et étiquetés comme tels : les consommations de démo (public/exemples/), le nom et l'adresse du site. Aucune donnée client réelle (Enedis, factures, PRM/PCE) dans le dépôt : data/prive/ est ignoré par Git.
D6 — Auth. AUTH_MODE=dev-stub : un utilisateur de démo fixe. L'auth réelle (phase 09) remplace le corps de getCurrentUser.
D7 — Migrations. Prisma Migrate. La migration init a été écrite à la main et appliquée sur un vrai PostgreSQL 16. Depuis, les évolutions passent par de nouvelles migrations (efa_reference_year, efa_surface_total) : on ne modifie jamais une migration fusionnée. Premier réflexe après un git pull : npm run db:migrate.
D8 — Prisma 7. Client généré dans src/generated/ (non versionné, régénéré par postinstall), connexion via @prisma/adapter-pg, config dans prisma.config.ts.
Décisions de la démo
D9 — Un lecteur par format externe. Un seul fichier connaît le format d'une source : climat/dju-source.ts (DJU), conformite/cabs-source.ts (Cabs), et batiment/ pour le référentiel OPERAT et les zones. Si le tuteur ou Mira change un format, on ne touche que ce lecteur. Remise en cause si : une source devient une API au lieu d'un fichier.
D10 — DJU : unité et rejet des années incomplètes. Le fichier mensuel est agrégé en DJU annuel ; une année dont les 12 mois ne sont pas tous couverts (jours_mesures) est refusée. Statuts d'une année : PAS_DE_CONSOMMATION → DJU_MANQUANT → ANNEE_INCOMPLETE → OK. Les DJU servent au suivi dans l'application ; OPERAT fait lui-même la correction climatique.
D11 — Année de référence. Une année complète de 12 mois entre 2010 et 2019, une par EFA, jamais une moyenne ; 2020 et 2021 sont exclues comme référence et du suivi des objectifs. Le comparateur suggère l'année la plus consommatrice ; le choix est enregistré dans EFA.referenceYear.
D12 — Conformité. Crelat = −40 % / −50 % / −60 % de Créf à 2030 / 2040 / 2050. Cabs = (CVC de la zone et de la tranche d'altitude + USE étalon) × surface, sans modulation. « Satisfait » signifie consommation ≤ objectif ; conforme si au moins une des deux méthodes l'est. Verdict principal = 2030 ; verdicts CONFORME / NON_CONFORME / INDETERMINE. Consommation suivie = dernière année complète hors 2020 et 2021. À vérifier : un seul seuil Cabs est lu pour les trois jalons.
D13 — Jamais de valeur réglementaire inventée. Une valeur Cabs absente donne VALEUR_ABSENTE, un code inconnu SOUS_CATEGORIE_INCONNUE, jamais 0. SCAP1812 et SCAP1813 (réserves froid, objet CVC vide) sont traités comme une valeur absente tant que l'arrêté n'a pas été lu. Le fichier Cabs ne couvre que CAP18 : le Cabs de l'EFA de bureaux (SCAP0401, CAP04) est non calculable.
D14 — Surface par EFA. EFA.surfaceTotal (nullable) porte la surface de l'EFA ; la règle de la tâche 1.3 devient « somme des lignes = surface de l'EFA », avec repli sur Building.surfaceTotal si le champ est vide. Raison : OPERAT déclare la surface par EFA, et un site à deux EFA (1 200 + 500 m²) ne tenait pas avec une surface unique de bâtiment.
D15 — Altitude du site. Pas de champ en base : la tranche d'altitude est une constante isolée (SITE_ALTITUDE_BAND = "<400", module bâtiment), marquée « à confirmer (IGN) ». Remplacée quand la tâche 1.1 saura lire l'altitude.
D16 — Station et zone. Building.climateZone contient provisoirement le code de la station de suivi (02037002). La zone climatique (H1a) se déduit du département (02) via le fichier OPERAT. La station OPERAT du département est 02320001 Saint-Quentin, à utiliser à l'export (phase 08). Un champ distinct demandera une PR schema.
D17 — Électricité annuelle. L'export Enedis ne donne que des kWh annuels alors que le modèle est mensuel. Pour la démo, les CSV d'exemple utilisent une répartition forfaitaire fictive (annuel ÷ 12), marquée FICTIF. À trancher avec Mira : détail mensuel disponible ou non.
D18 — Une EFA affichée à la fois. Les pages surfaces, comparateur et conformité travaillent sur la première EFA du bâtiment ; le seed place la restauration en premier. Le sélecteur d'EFA (paramètre efaId sur les API) reste à faire.
D19 — Tableau de bord en lecture seule. /dashboard n'écrit rien en base et ne recalcule rien : loadDashboard() appelle les cinq chargeurs (bâtiment, surfaces, climat, comparateur, conformité) avec Promise.allSettled, et la fonction pure buildSynthesis décide de l'affichage. Chaque source se dégrade seule (jamais de 500) et chaque manque donne un message et une action (la « prochaine étape » est le premier manque dans l'ordre : base, connexion, bâtiment, surfaces, consommations, DJU, année de référence, Cabs). L'étape « bâtiment » n'a pas de lien tant que les tâches 1.1 / 1.2 n'ont pas d'écran. À revoir quand les modules bâtiment et sécurité auront de vraies pages.
D20 — Référentiel d'activités OPERAT v9.0. Importé tel quel dans ReferenceData (types CATEGORY et SUBCATEGORY), idempotent ; une sous-catégorie encore utilisée par une ligne de surface n'est jamais supprimée (avertissement). Mise à jour vers une v9.1 : remplacer le fichier dans data/referentiels/operat/ et relancer npm run db:import. Les codes ont des longueurs variables (catégories CAP18 ou CAP0501, sous-catégories à 4 ou 6 chiffres) : à retenir pour l'export OPERAT (phase 08). Une valeur étalon vide est lue comme absente (null), jamais comme 0.
